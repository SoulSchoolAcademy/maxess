# 27 — MAXESS GROOVE EMBED-ONLY DELIVERY LAW

Status: LOCKED PROJECT LAW
Version: 1.0

## Scope

This law applies specifically to the current MAXESS Results project and overrides generic delivery habits whenever the requested deliverable is the MAXESS Results experience for Groove.

## Primary delivery rule

THE ONLY USER-FACING CODE DELIVERABLE FOR MAXESS RESULTS IS THE COMPLETE GROOVE EMBED CODE.

Do not deliver a standalone HTML document as the requested MAXESS Results production artifact.
Do not deliver a tinyized preview.
Do not deliver a prototype.
Do not deliver pseudo-code.
Do not deliver abbreviated code.
Do not deliver a loader, redirect, iframe wrapper, placeholder, shell, or partial implementation as a substitute for the complete Groove embed.

The production deliverable must be the actual self-contained Groove embed intended to be pasted into Groove.

## Complete-product rule

The embed is not merely a visual Results page.

It is the complete MAXESS Results experience required for public use, including every approved section, interaction, transition, personalization layer, result interpretation, visualization, Naya experience, pathway, AI mastery presentation, downstream NayaNET continuation, video/content presentation, membership presentation, buttons, CTAs, accessibility behavior, responsive behavior, error handling, and graceful degradation required by the current project specification.

Nothing important may be omitted merely to reduce code size.

## Minimum implementation threshold

For this project, a production MAXESS Groove embed must contain THOUSANDS OF LINES OF COMPLETE IMPLEMENTATION.

The minimum threshold is 3,000 lines unless a future project authority explicitly changes it.

The line count is a release floor and a regression detector, NOT the definition of quality.

A larger file is not automatically better.
A smaller file is not automatically better.

The governing objective is:

MAXIMUM COMPLETE PRODUCT VALUE INSIDE GROOVE.

If the complete experience legitimately requires 4,000, 5,000, 6,000+ lines, preserve the required implementation.

Never delete meaningful product capability merely to get under a line-count target.

## Optimization law

OPTIMIZE FOR GROOVE.

DO NOT TINYIZE FOR GROOVE.

Groove optimization means:
- self-contained delivery
- scoped CSS
- collision resistance
- deterministic initialization
- defensive JavaScript
- minimal unnecessary dependencies
- reliable responsive behavior
- graceful failure
- efficient rendering
- strong performance
- maintainable structure
- complete product capability

Groove optimization does NOT mean:
- removing sections
- removing interactions
- replacing rich components with placeholders
- deleting personalization
- deleting the Naya experience
- deleting the 18-area pathway/library
- deleting the downstream NayaNET experience
- deleting video/content required by the approved experience
- replacing the final product with a tiny demonstration

## Source-of-truth rule

Before producing or modifying the embed:

1. Read the current repository memory and locked specifications.
2. Inspect the authoritative Results source.
3. Inspect the current Groove embed implementation.
4. Inspect relevant Git history and previous approved implementations when needed.
5. Preserve valuable working functionality.
6. Identify regressions before making changes.
7. Build the complete current product.
8. Validate the Result Contract and end-to-end data flow.
9. Verify the entire user journey.
10. Only then produce the Groove embed.

## Single-embed law

The final production deliverable must be one complete Groove embed.

No hidden competing Results applications.
No multiple generations stacked inside the same embed.
No legacy page hidden underneath a new page.
No `display:none` strategy used to disguise competing implementations.
No document-wide takeover used as a substitute for proper architecture unless explicitly required by the Groove environment and proven safe.

One authoritative Results experience.
One renderer.
One result truth.
One complete embed.

## Product-completeness gate

Before delivery, verify that the embed contains and connects all required pieces from the current MAXESS specification, including where applicable:

- authoritative overall score
- mastery level
- five-dimension capability signature
- accessible dimension equivalents
- natural advantage
- highest-leverage opportunity
- meaningful pattern interpretation
- OH... THAT'S WHY synthesis
- Naya interpretation
- Master Key revelation
- personalized AI opportunities
- 18-area AI mastery pathway/library
- personalized priority areas
- pathway progression
- continuation experience
- approved NayaNET downstream experience
- approved video/content experience
- approved membership presentation
- correct buttons and CTAs
- save/download where specified
- responsive mobile composition
- reduced-motion behavior
- accessibility
- error states
- graceful degradation
- real result handoff

## Truth rule

Never invent result data.
Never fabricate personalization.
Never replace missing authoritative data with fake production values.

The assessment engine remains the authority for assessment truth.
The Results embed consumes and validates the Result Contract.

## Release-quality rule

The embed is not ready because:
- it is large
- it renders some content
- GitHub accepted it
- a file exists
- a workflow passed a superficial check
- the page looks beautiful

It is ready only when the complete product has been verified against the current MAXESS release gate.

## Final directive

BUILD THE FULL MEAL DEAL.

Do not give the user a miniature representation of the product.
Give them the actual Groove production experience.

MAXESS Results → complete Groove embed → complete working product → ready for real-world testing and release.

The standard is not:

"How little code can we get away with?"

The standard is:

"How much exceptional, useful, reliable, beautiful, personalized MAXESS experience can we deliver inside Groove without unnecessary waste?"

That is the law.
