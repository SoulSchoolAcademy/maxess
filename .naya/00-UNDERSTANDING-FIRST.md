# 00 — UNDERSTANDING-FIRST MASTER GATE

Status: AUTHORITATIVE PROJECT LAW
Priority: HIGHEST PROJECT-LEVEL EXECUTION PRIORITY
Scope: All consequential AI/agent work in the MAXESS repository.

## PURPOSE

This file establishes the non-negotiable rule that understanding precedes execution.

MAXESS must never be modified by an AI that has merely recognized the apparent request. The executor must first understand the product, repository, architecture, source-of-truth relationships, existing working behavior, deployment path, user experience, design language, growth objective, constraints, and acceptance criteria.

## PRIME LAW

# UNDERSTAND BEFORE YOU EXECUTE.

No consequential implementation may begin until the executor has:

1. Read the applicable Naya governance chain.
2. Inspected the relevant repository structure and current source.
3. Identified the authoritative source of truth.
4. Distinguished source files from generated artifacts, legacy/prototype files, specifications, and release infrastructure.
5. Understood what already works and what must be preserved.
6. Verified the current production/deployment path when relevant.
7. Identified contradictions, uncertainties, missing information, and risks.
8. Reconciled those findings into one coherent mental model.
9. Formulated a complete implementation and verification plan.
10. Passed the Understanding Gate below.

If any material item remains unknown or contradictory, STOP and investigate. Do not guess through a material uncertainty.

## MASTER TRIGGER

When the human says:

> **GO — MASTER NAYA**

interpret this as activation of the MAXESS Master Understanding Protocol.

It does NOT mean “start coding immediately.”

It means:

**READ → MAP → VERIFY → RECONCILE → PLAN → PASS THE UNDERSTANDING GATE → EXECUTE → TEST → SCORE → IMPROVE → VERIFY → DELIVER**

## UNDERSTANDING GATE

Before implementation, the executor must be able to explain clearly:

### PRODUCT
- What MAXESS is.
- What the current Results experience is for.
- What human outcome the experience must create.
- How Results connects to Naya and NayaNET.

### ARCHITECTURE
- What the authoritative Results source is.
- What generates the deployed artifact.
- What generates any Groove embed/artifact.
- What deploys it.
- What verifies it.
- Which files are source, generated, legacy, specification, or release infrastructure.

### DATA
- Where result data comes from.
- How scoring works.
- How the Result Contract works.
- How personalization works.
- How the five dimensions and 18 AI mastery areas are represented.

### DESIGN
- What NayaNET's existing visual language is.
- Which existing buttons, icons, controls, typography, motion, surfaces, and interaction patterns must be reused or adapted.

### EXPERIENCE
- What the user should understand, feel, discover, and do from arrival through final CTA.
- Why the sequence creates trust and momentum.

### GROWTH
- What the intended journey is: understand → trust → care → continue → engage → convert → return → share.
- What the primary next action is.
- Why that action is earned by the preceding experience.

### QUALITY
- What 9.9 means for this project.
- What would prevent the result from being 9.9.
- How functional, visual, UX, accessibility, performance, growth, architecture, and deployment quality will be verified.

## REQUIRED READINESS STATE

Before implementation, the executor must have a concrete internal/external readiness statement containing:

- WHAT I UNDERSTAND
- WHAT EXISTS
- WHAT IS AUTHORITATIVE
- WHAT MUST BE PRESERVED
- WHAT IS VERIFIED BROKEN OR MISSING
- WHAT REMAINS UNCERTAIN
- WHAT I WILL CHANGE
- WHAT I WILL NOT CHANGE
- HOW I WILL VERIFY IT
- WHAT DEFINES DONE

If material uncertainty remains, status is **BLOCKED — UNDERSTANDING INCOMPLETE**.

## NO BLIND EXECUTION

Never:

- code from the first request without repository inspection;
- assume a filename is authoritative because it is large or recent-looking;
- create another parallel implementation without architectural justification;
- replace working architecture with a tiny shortcut;
- reduce functionality merely to reduce code;
- invent a weaker design system when the project already has one;
- declare success because code compiles or a page loads;
- claim 9.9, AAA, tested, complete, or production-ready without evidence.

## PRESERVATION LAW

**PRESERVE WHAT WORKS. REPAIR WHAT DOESN'T. INTEGRATE WHAT IS MISSING. REMOVE ONLY WHAT IS PROVEN TO BE WRONG.**

Before replacing anything, determine what it does, why it exists, whether it still serves its purpose, and whether it can be improved without destroying working value.

## SOURCE-OF-TRUTH LAW

When sources disagree:

1. Identify the conflict.
2. Determine which source is authoritative.
3. Verify against the current architecture and deployment path.
4. Resolve the conflict deliberately.
5. Record a reusable lesson if the conflict exposes a process weakness.

Never silently choose the easiest source to edit.

## MULTI-AI / MULTI-AGENT LAW

If another AI, agent, tool, or specialist is involved, the same understanding must be transferred before that agent executes.

No downstream agent may receive only an isolated task fragment when the missing project context could materially change its implementation.

The coordinating AI must communicate:

- the mission;
- authoritative sources;
- protected functionality;
- relevant architecture;
- exact requested delta;
- constraints;
- acceptance criteria;
- verification requirements;
- known risks and unresolved questions.

Every agent operates from one shared project understanding.

## EXECUTION SEQUENCE

### PHASE 0 — UNDERSTAND
Read governance and project instructions.

### PHASE 1 — DISCOVER
Inspect repository, source, artifacts, deployment, dependencies, assets, data contracts, workflows, and known-good versions.

### PHASE 2 — RECONCILE
Resolve source-of-truth conflicts and distinguish known, inferred, assumed, and unknown information.

### PHASE 3 — PLAN
Define preservation, repair, redesign, integration, generation, testing, and release steps.

### PHASE 4 — GATE
Pass the Understanding Gate. Otherwise BLOCK.

### PHASE 5 — EXECUTE
Modify only the authoritative implementation path.

### PHASE 6 — VERIFY
Build, inspect, test, and verify the actual artifact and deployment.

### PHASE 7 — OSCAR
Attack the result for missing requirements, regressions, weak UX, weak language, visual inconsistency, accessibility problems, technical fragility, and growth friction.

### PHASE 8 — IMPROVE
Fix material findings.

### PHASE 9 — RETEST
Repeat verification after fixes.

### PHASE 10 — DELIVER
Only deliver when the final live/target artifact is verified.

## DEFINITION OF DONE

The work is not done because the requested code exists.

It is done only when the actual experience satisfies the complete project specification and has been verified against the intended human outcome.

The final question is:

> **Would we confidently put this exact current result in front of thousands or millions of people and say this is MAXESS, this is NayaNET, and this represents our standard?**

If not, continue.

## CORE PRINCIPLE

> **Never optimize for the appearance of completion. Optimize for actual excellence.**

The project standard remains:

**Serve humans. Tell the truth. Think deeply. Simplify intelligently. Build beautifully. Optimize relentlessly. Ship AAA. Scale wisdom.**
