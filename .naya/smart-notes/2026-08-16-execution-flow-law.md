# Naya Smart Note — Execution Flow Law

**Date:** 2026-08-16  
**Authority:** Digital Codex / Naya Master / Execution Process  
**Status:** Authoritative operating rule

## Core lesson

The system must not fall into repeated planning, blocker, or permission loops. The purpose of the process is to move work upstream toward a concrete, testable result.

## Execution laws

1. **Read First, Then Execute.** Read the authoritative repository governance, project memory, source-of-truth artifact, and relevant directives before acting.
2. **Groove access is not an upstream engineering blocker.** If direct Groove publishing is unavailable, complete every upstream task that can be completed: implementation, integration, personalization, QA, data integrity, responsiveness, accessibility, conversion, and deployment readiness.
3. **Produce the actual artifact.** When engineering is complete, deliver the complete self-contained Groove-compatible artifact. Never substitute a patch, excerpt, placeholder, or assembly instructions when the complete artifact is the required deliverable.
4. **The user is the final Groove visual tester when direct publication is unavailable.** Hand off the concrete link/artifact and a concise verification checklist rather than repeatedly explaining the deployment limitation.
5. **3-iteration target.** Normally reach a concrete testable artifact or link within 1–3 execution cycles.
6. **10-iteration loop-failure rule.** If 10 consecutive cycles occur without a concrete testable deliverable, stop and diagnose the process. Treat that as a system failure, not normal progress.
7. **Every iteration moves upstream.** Preserve what works, repair weaknesses, improve quality, learn from failures, remove duplication, and never regress.
8. **Never claim a stronger state than reality.** Distinguish clearly between ENGINEERING COMPLETE, READY FOR GROOVE TEST, and LIVE VERIFIED.
9. **Completion handoff.** State what was actually completed, provide the actual test link or complete deployable artifact, and provide a concise verification checklist.
10. **Self-improvement.** After meaningful work, record useful lessons as organized Smart Notes so future executions begin with accumulated knowledge rather than repeating old mistakes.

## Required completion language

When the engineering artifact is ready:

> **ENGINEERING COMPLETE — READY FOR GROOVE TEST.**
>
> Here is the testable link/artifact.
>
> Here is exactly what changed.
>
> Here is exactly what to verify.

Do not call this **LIVE VERIFIED** until the real public URL has actually been verified after deployment.

## Optimization principle

The goal is not merely fewer messages. The goal is fewer wasted iterations. Each cycle should increase certainty, quality, completeness, and readiness. The system should continuously move from uncertainty → understanding → execution → refinement → concrete handoff.

## North Star

**Execute → Improve → Verify → Hand Off → Learn → Move Upstream.**

No unnecessary loop. No regression. No repeated blocker explanation when upstream work can continue.
