# 0. WHY THIS CODEX EXISTS

AI is exceptionally good at generating possibilities. It is not automatically reliable at finishing complex work.

The recurring failures this Codex exists to prevent include:

1. Wrong result — the output does not solve the actual problem.
2. Zero execution — the AI describes work but changes nothing.
3. Wrong artifact — the AI edits a copy, preview, legacy file, or non-authoritative source.
4. Stale delivery — an older artifact is returned as the new result.
5. Partial execution — some requirements are implemented and others disappear.
6. Fragment delivery — a snippet, patch, wrapper, mockup, or prototype is presented as the complete product.
7. Context loss — previous decisions, constraints, or completed work disappear.
8. Regression — new work breaks something that already worked.
9. Destructive simplification — working complexity is replaced with a smaller but weaker implementation.
10. Requirement dropout — one or more requested items are silently forgotten.
11. False completion — the AI says “done” without evidence.
12. Deployment parity failure — the repository changes but the public product does not.
13. Runtime failure — the code exists but the real user experience does not work.
14. Data failure — real data is replaced by fixtures, fallbacks, or invented values.
15. Visual quality failure — technically correct work remains mediocre.
16. Narrative failure — individual sections work but the whole experience does not make sense.
17. Scope drift — the AI silently changes the assignment.
18. Endless iteration — improvements never become stable, recoverable versions.
19. Repeated failure — the same failure happens again because the process did not learn.
20. Human memory burden — the user must repeatedly explain the same requirements.

The Digital Codex turns these failures into explicit definitions, gates, procedures, evidence requirements, and learning mechanisms.

It is not a prompt.
It is not a style guide.
It is not a suggestion.
It is the operating protocol for reliable AI execution.

# 2. THE GOVERNANCE STACK

The system is organized into layers so documents do not compete with each other.

## LAYER 1 — NAYA-MASTER
Defines overall mission, identity, role, philosophy, and master operating context.

**Question:** Who are we and what are we trying to accomplish?

## LAYER 2 — NAYA-GOVERNANCE
Routes the system, defines authority, reading order, escalation, and document relationships.

**Question:** Which rules and documents govern this task?

## LAYER 3 — NAYA-LAW
Contains concise, durable, non-negotiable laws.

**Question:** What may never be violated?

## LAYER 4 — DIGITAL CODEX
Contains the operational execution system: vocabulary, states, gates, workflows, failure handling, verification, evidence, iteration, and learning.

**Question:** Exactly how must AI execute?

## LAYER 5 — PROJECT / PRODUCT INSTRUCTION SET
Contains the specific blueprint for the thing being built.

Example: `.naya/MAXESS-RESULTS-MASTER-INSTRUCTION-SET.md`

**Question:** What exactly should this particular product become?

## LAYER 6 — EXECUTION LOCK / TASK STATE
Contains the current execution number, baseline, source lock, active checklist, risks, and state of a specific implementation.

**Question:** What exactly are we changing right now, from which version, and what remains?

## LAYER 7 — PROJECT MEMORY
Contains durable facts, architecture, decisions, assets, constraints, lessons, and reusable context.

**Question:** What must the AI remember about this project?

## LAYER 8 — AUTHORITATIVE ARTIFACT
The actual source that must change.

**Question:** What exact thing is being modified?

## LAYER 9 — USER-FACING STATE
The actual deployed/public/runtime result.

**Question:** What does the human actually experience?

Therefore:

**MISSION → GOVERNANCE → LAW → CODEX → PRODUCT BLUEPRINT → EXECUTION STATE → MEMORY → ARTIFACT → USER EXPERIENCE**

No layer may pretend to be another layer.

A partial change intended to be applied to an existing artifact.

### SNIPPET
A fragment of code or content.

An intentionally incomplete exploratory implementation.

### PREVIEW
A representation used for inspection that is not necessarily the authoritative production source.

Any statement that work was changed, fixed, tested, preserved, deployed, verified, or completed. Claims require evidence.

# 7. ABSOLUTE PRESERVATION RULE

Before changing an existing system:

1. Inspect the current master artifact.
2. Establish an untouched freeze/recovery point.
3. Inventory the existing implementation.
4. Identify every working component.
5. Identify every protected dependency.
6. Trace the deployment path.
7. Record the baseline.
8. Only then modify.

Use:

**PRESERVE → UNDERSTAND → IMPROVE → INTEGRATE → TEST → SCORE → FREEZE**

Never rebuild simply because rebuilding is easier.
Never replace a complete working artifact with a smaller prototype.
Never remove functionality merely because it is inconvenient to preserve.
Every intentional removal must have a reason and be checked against the directive.

---

# 8. PRESERVATION MAP

Every consequential existing component must be classified.

**PRESERVE** — Working and intentionally protected.

**REPAIR** — Functionally present but below the desired quality standard.

**RESTRUCTURE** — Correct material, wrong order, grouping, hierarchy, or presentation.

**REPLACE** — Genuinely fails the requirement and needs a superior implementation.

**ADD** — Required but missing.

**REMOVE** — Redundant, misleading, harmful, explicitly rejected, or unnecessary.

The AI must never silently convert PRESERVE into REMOVE.

---

# 9. BASELINE LAW

Before modification, record enough information to prove what changed.

Where technically available:

- repository;
- branch/ref;
- commit SHA;
- authoritative file path;
- file/blob SHA;
- line count or size where useful;
- structural markers;
- key content markers;
- asset references;
- deployment target;
- public URL where applicable;
- current user-facing state where applicable.

For visual work, baseline evidence should include the relevant rendered state when feasible.

Never modify first and discover the baseline afterward.

---

# 10. SOURCE-LOCK LAW

Before editing, establish this chain:

```text
REPOSITORY
↓
BRANCH / REF
↓
AUTHORITATIVE SOURCE
↓
BUILD / GENERATION PATH
↓
DEPLOYMENT ARTIFACT
↓
PUBLIC / USER-FACING TARGET
```

The executor must be able to answer:

> If I modify this exact source, why will the user see the requested change at the requested destination?

If the causal chain cannot be demonstrated:

**BLOCKED — TARGET CONNECTION UNPROVEN.**

---

# 11. COMPLETE REQUIREMENT INVENTORY

Before substantial execution, convert the directive into a traceability matrix.

For every material requirement record:

```text
ID
REQUIREMENT
WHY IT EXISTS
IMPLEMENTATION LOCATION
EXPECTED CHANGE
PRESERVATION RISK
VERIFICATION METHOD
EVIDENCE LOCATION
STATUS
```

Every requirement must end as one of:

- DONE
- BLOCKED
- NOT APPLICABLE WITH REASON

There is no implicit completion.

---

# 12. REQUIREMENT → IMPLEMENTATION → VERIFICATION

Every requirement must have a three-part trace:

**REQUIREMENT → IMPLEMENTATION → VERIFICATION**

Example:

Requirement: The user's score must be the first visual priority.

Implementation: Place the live score and Orb at the top of the rendered experience; remove competing hero content.

Verification: Inspect DOM order and rendered viewport; confirm the real score appears before secondary report content.

A code fragment resembling the requested feature is not enough.

---

# 13. EXECUTION QUEUE

Before substantial modification, derive an execution queue.

Every task receives a state:

**PENDING → IN PROGRESS → DONE / BLOCKED / NOT APPLICABLE**

Do not mark DONE based on intention.

A task is DONE only after its verification method passes.

For large interfaces, execute section by section while maintaining a global checklist.

Section-by-section means:

**GLOBAL MAP → SECTION → IMPLEMENT → VERIFY → NEXT SECTION → GLOBAL REASSESSMENT**

---

# 14. ZERO-MATERIAL-CHANGE GATE

If the requested work requires a change and the authoritative artifact has no meaningful diff:

# BLOCKED — ZERO MATERIAL CHANGE.

The following do NOT override it:

- sending a new link;
- generating a new message;
- renaming a file;
- creating a preview;
- copying the old file;
- generating a download;
- describing intended changes;
- claiming that the change “should be there”;
- successful tool/API response without artifact verification.

If zero change occurs, diagnose:

1. Wrong file.
2. Wrong branch.
3. Wrong source of truth.
4. Write failed.
5. Write targeted a copy.
6. New work was overwritten by old work.
7. Change was not material to the request.
8. Build/deployment did not consume the changed source.
9. Requirement was misunderstood.
10. Requested result is not represented in the implementation.

Fix the mechanism before claiming success.

---

# 15. MINIMUM DELTA / COMPLETENESS GATE

Code size alone never proves quality.

However, the scope of the diff must be proportionate to the scope of the directive.

A request for a complete multi-section redesign cannot normally be satisfied by a few unrelated lines.

A small diff may be valid when the existing architecture already contains the required system, but the executor must explain why and provide evidence.

The test is:

> **Did the complete requested scope actually change, or did the executor produce a convenient fragment?**

If material requirements remain incomplete:

**BLOCKED — PARTIAL EXECUTION.**

---

# 16. COMPLETE-PRODUCT LAW

When the user asks for a full product, full page, full file, complete code, or complete implementation, deliver the complete relevant artifact.

Do not substitute a snippet, patch, wrapper, redirect, loader, mockup, fixture, placeholder, simplified prototype, or old version.

If the user asks for a patch, provide a patch.
If the user asks for full code, provide full code.
If the user asks for a preview, provide a preview and label it as such.

Never call one artifact category another.

---

# 17. WRITE → REFETCH → DIFF

After every consequential write:

1. Re-fetch the exact artifact.
2. Confirm expected content is present.
3. Compare with the baseline.
4. Inspect the actual diff.
5. Confirm the file is the source-locked target.
6. Confirm each changed area maps to a requirement.
7. Confirm no unexpected destructive changes occurred.

A successful write API response is not product proof.

---

# 18. WRONG-FILE GATE

ACTUAL MODIFIED FILE

# 22. FAILURE CLASS CATALOG

## F01 — WRONG RESULT
Cause: outcome poorly defined or misunderstood.
Control: explicit outcome + acceptance criteria + scorecard.

## F02 — ZERO EXECUTION
Cause: AI generated explanation instead of changing the artifact.
Control: zero-material-change gate + refetch + diff.

## F03 — WRONG SOURCE
Cause: non-authoritative file selected.
Control: source-lock + wrong-file gate.

## F04 — STALE ARTIFACT
Cause: old version returned.
Control: SHA/version/distinctive-marker verification.

## F05 — PARTIAL EXECUTION
Cause: some requirements implemented and others dropped.
Control: requirement traceability + completeness gate.

## F06 — FRAGMENT DELIVERY
Cause: snippet/patch/prototype presented as product.
Control: artifact classification + complete-product law.

## F07 — CONTEXT LOSS
Cause: reliance on conversational memory.
Control: project memory + instruction sets + execution locks.

## F08 — REGRESSION
Cause: new work damages existing functionality.
Control: preservation map + regression test + recovery freeze.

## F09 — DESTRUCTIVE SIMPLIFICATION
Cause: working system replaced by easier smaller implementation.
Control: preservation law + diff review + architecture inventory.

## F10 — REQUIREMENT DROPOUT
Cause: long directive loses items.
Control: numbered traceability matrix.

## F11 — FALSE COMPLETION
Cause: narrative outruns evidence.
Control: claim-evidence rule.

## F12 — DEPLOYMENT PARITY FAILURE
Cause: repository changed but public target did not.
Control: deployment chain mapping + live check.

## F13 — RUNTIME DATA FAILURE
Cause: real data contract not connected.
Control: runtime data gate + multiple test states.

## F14 — VISUAL QUALITY FAILURE
Cause: functional implementation is aesthetically weak.
Control: visual scorecard + independent Oscar review.

## F15 — NARRATIVE FAILURE
Cause: sections individually work but the story does not.
Control: macro flow audit.

## F16 — SCOPE DRIFT
Cause: executor substitutes its preferred task.
Control: directive lock + requirement reconciliation.

## F17 — TOOL FAILURE
Cause: read/write/build/publish operation fails.
Control: verify tool result and re-fetch actual state.

## F18 — SOURCE CHAOS
Cause: multiple competing “final” artifacts.
Control: source registry + authority hierarchy.

## F19 — ENDLESS ITERATION
Cause: no successful freeze/recovery point.
Control: versioning + freeze gate.

## F20 — FAILURE WITHOUT LEARNING
Cause: mistake repeated without governance change.
Control: failure → safeguard loop.

## F21 — HUMAN MEMORY BURDEN
Cause: user repeatedly restates requirements.
Control: durable project memory and instruction-set updates.

## F22 — LOCAL OPTIMIZATION
Cause: one component improves while the whole system worsens.
Control: macro → micro → macro review.

## F23 — CLAIM/EVIDENCE MISMATCH
Cause: language says more than evidence proves.
Control: evidence-bound completion vocabulary.

## F24 — DEPENDENCY BLINDNESS
Cause: component changed without understanding integrations.
Control: dependency inventory and protected-interface map.

## F25 — VISIBILITY FAILURE
Cause: implementation exists but user cannot see/use it.
Control: runtime + public parity verification.

# 23. MULTI-LAYER SOLUTION MODEL

Every significant failure should be attacked from four perspectives.

## LAYER A — LANGUAGE
Make the instruction unambiguous. Define terms. Define success. Remove interpretation gaps.

## LAYER B — PROCESS
Create mandatory sequence and checklists. Prevent omission.

## LAYER C — TOOLING
Use diffs, hashes, tests, screenshots, runtime checks, deployment checks, and repository inspection. Make truth observable.

## LAYER D — GOVERNANCE
Convert repeated lessons into permanent rules and gates.

The strongest solution uses all four.

# 26. SCORECARDING MASTER KEY

Every major deliverable must be evaluated using:

**KNOW → DEFINE → WEIGHT → INSPECT → SCORE → DIAGNOSE → IMPROVE → RE-SCORE → PROVE → FREEZE**

Universal score scale:

**0–10 per category.**

Weights:

**must total exactly 100%.**

A 10 means exceptional evidence, not enthusiasm.

For visual/product work, score at least:

- correctness;
- completeness;
- user experience;
- visual quality;
- clarity/scannability;
- emotional impact;
- functionality;
- accessibility;
- performance;
- conversion/action clarity where relevant.

The categories and weights must match the actual objective.
Never manipulate weights to manufacture a desired score.

# 34. DEPLOYMENT PARITY LAW

For live work:

**SOURCE → BUILD → DEPLOYMENT → PUBLIC TARGET**

must be traceable.

Repository change is not sufficient.
Public change is not sufficient if the source of truth is wrong.
Both must agree.

If GitHub changed but the live page did not:

**BLOCKED — DEPLOYMENT PARITY FAILURE.**

If the page is blank or broken:

**BLOCKED — LIVE FAILURE.**

Do not speculate about cache, publishing, timing, or browser state before testing.

# 35. PRINT / PDF VERIFICATION

When a product includes PDF/print:

- use a dedicated print stylesheet where appropriate;
- remove web-only controls;
- ensure text contrast remains readable;
- establish intentional page breaks;
- preserve important hierarchy;
- prevent awkward section splits;
- verify both screen and print assumptions;
- inspect the actual generated result, not just CSS.

A web page that looks good but produces an unreadable PDF is not fully complete when PDF is required.

# 44. FAILURE RESPONSE PROTOCOL

When execution fails:

**ACKNOWLEDGE → CONTAIN → DIAGNOSE → CORRECT → VERIFY → PREVENT → RECORD → RETEST**

### ACKNOWLEDGE
State exactly what failed.

### CONTAIN
Prevent further damage or regression.

### DIAGNOSE
Find the actual root cause, not merely the visible symptom.

### CORRECT
Fix the mechanism.

### VERIFY
Prove the correction.

### PREVENT
Add a rule, test, gate, automation, or memory safeguard.

### RECORD
Capture the reusable lesson.

### RETEST
Prove the original failure no longer occurs.

An apology is not a correction.

# 45. REPEATED FAILURE ESCALATION

If the same failure class occurs twice:

**ADD OR STRENGTHEN A MANDATORY GATE.**

If it occurs three times:

**ADD A DETERMINISTIC OR AUTOMATED CHECK WHERE POSSIBLE.**

If it occurs four times:

# ROOT-CAUSE LOCKDOWN.

During Root-Cause Lockdown:

1. Stop new cosmetic/product work.
2. Re-map the entire failing chain.
3. Identify the authoritative source.
4. Re-establish the baseline.
5. Reproduce the failure.
6. Isolate the mechanism.
7. Create a regression test.
8. Confirm the test fails before the fix.
9. Apply the fix.
10. Confirm the test passes after the fix.
11. Add the safeguard to governance.
12. Resume normal work only after the system is demonstrably safer.

# 48. NO-OP DETECTION

A no-op is not limited to a zero-byte diff.

A material no-op includes:

- changing irrelevant comments while requested UI remains unchanged;
- changing a preview instead of the authoritative source;
- changing an unused component;
- changing code that is not loaded by the target;
- adding dead CSS/HTML that never renders;
- changing a fallback while real data bypasses it;
- creating a new file that is never integrated;
- changing a generated output that is overwritten during deployment.

Verification must test both:

**ARTIFACT CHANGE**
and
**OUTCOME CHANGE.**

# 49. SCOPE CONTROL

The executor must distinguish:

### MUST
Explicit requirement.

### SHOULD
Strong recommendation.

### MAY
Optional enhancement.

### MUST NOT
Explicit prohibition.

A SHOULD must not override a MUST.
A MAY must not consume effort that prevents a MUST from being completed.

When scope becomes too large for one execution, split into explicit phases rather than silently delivering an incomplete result.

# 50. QUALITY VS COMPLETION

A product can be complete but low quality; beautiful but incomplete; functional but unverified; verified but not deployed; deployed but regressed; correct but confusing; technically sound but psychologically ineffective.

Therefore “complete” and “high quality” are separate gates.

Completion proves the requested scope exists and works.
Scorecarding proves how well it works.
Both are required for AAA delivery.
